# GD-001 — API Good Doggy v1, revisión 0.2.0 (PROPUESTA)
Base /api/v1/integrations/gooddoggy/; barra final canónica. Solo GET (HEAD/OPTIONS si se prueban seguros), otros métodos 405; no redirecciones ni fallback a rutas públicas, administrativas, móviles o de cliente. No endpoints implementados en este PR. OpenAPI es el contrato de estructura; este documento define semántica, autorización y pruebas de invariantes.
## 1. Autenticación y autorización
Propuesta S2S: bearer opaco de alta entropía, hash en servidor, principal exclusivo de integración sin usuario staff, cookies ni permisos heredados. TLS, rotación/revocación, rate limit por credencial y tenant, auditoría redactada, sin tokens/PII. Tenant, sucursales y scopes resueltos por servidor; parámetro selecciona, nunca autoriza.
| Operación | Scope base | Condiciones adicionales |
|---|---|---|
| products, products/{id} | catalog.read | proyección catálogo, sin precios/stock/promos |
| catalog/search | catalog.read | oferta comercial: prices.read + inventory.read; promociones: promotions.read; beneficio: prices.read + promotions.read; metadata branch: branches.read |
| availability | inventory.read | disponibilidad agregada por variante/sucursal; identidad individual de oferta usada exige prices.read |
| prices | prices.read | precio configurado de estante; ofertas usadas o bajo pedido exigen inventory.read para no revelar disponibilidad por su mera existencia |
| promotions | promotions.read | beneficio monetario/porcentual exige prices.read; no cupones privados |
| branches | branches.read | sucursales autorizadas activas, no contactos |
| services | services.read | DESHABILITADO hasta acreditar fuente publicable; futuro stock de repuestos exige inventory.read |
| orders/{id}, repairs/{id} | orders.read / repairs.read | DESHABILITADOS hasta grant de cliente aprobado; sin 200, 404 uniforme, no grant header actual |
| sync/changes | sync.read | domain product/catalog.read, inventory/inventory.read, price/prices.read, promotion/promotions.read, branch/branches.read; composición de oferta idéntica |
| health | health.read | estado mínimo, sin infraestructura |
Scopes independientes. catalog.read no permite inferir otros dominios por selección, orden, filtros, conteos, existencia de filas, error, tiempo, caché o ETag. Filtros sku/model/capacity/color fuera de catálogo exigen catalog.read; filtro branch_id en catálogo exige branches.read, en dominio precio/inventario selecciona solo alcance ya concedido. IDs opacos de sucursal son parte de identidad del dominio autorizado, no conceden metadata. Rechazar scope/field explícito no permitido 403; objeto ajeno/inexistente 404 indistinguible; no incluir null para dato no autorizado (omitir opcional). Revalidar en cada petición, incluso 304.
## 2. Proyección, búsqueda y fields
OpenAPI define 22 esquemas específicos cerrados (additionalProperties:false), formatos, required, nullable y límites. Campos no declarados nunca salen, ni de forma anidada. Identidades, discriminadores, versiones, fechas y demás campos required no pueden eliminarse con fields. Listas: results,next_cursor,snapshot_at,watermark obligatorios. Tamaño 20 por defecto, 50 máximo, cursor opaco hasta 2048 caracteres; q hasta 120; filtros hasta 128. Campos opcionales se omiten si no se solicitaron o autorizaron; null solo si autorizado y valor desconocido/no aplicable según schema.
- products/detail: fields CSV de name,sku,model,capacity,color,image_url,commercial_url,warranty; product_id,variant_id,model_id,data_version,observed_at,condition son obligatorios.
- catalog/search: fields CSV de product.name, product.sku, product.model, product.capacity, product.color, product.image_url, product.commercial_url, product.warranty, promotions, promotions.benefit, branch. Campos requeridos de Product conservados; promotions.benefit exige promotions y ambos scopes. No selecciones arbitrarias o duplicadas. fields desconocido/combinar dependencias inválidas: 400. Si fields se omite, defaults autorizados. Si no hay ambos scopes comerciales, fila catálogo con offer_kind/offer_id/branch_id null y sin price/availability/branch/used_details. include_offers=false fuerza catálogo; true exige catalog.read+prices.read+inventory.read o 403; ausente incluye ofertas únicamente con ambos. Fila de oferta tiene price y availability obligatorios e inseparables, no removibles por fields. used_details obligatorio en oferta usada. Metadata branch opcional y scope branches.read. No devolver filas de oferta para inferir disponibilidad oculta.
- promotions: fields solo benefit; el resto obligatorio. En endpoints sin opcionales no existe fields. ETag de representación exacta, ligado a tenant, alcance, scopes, filtros, fields, include_offers y versión; autorización previa al 304. Datos sensibles private/no-store. Feed no usa 304 como sustituto del cursor.
- Descripciones y HTML no salen. Solo nombre, atributos reales y links HTTPS de catálogo autorizado; ninguna URL de tracking, secreto, query privada o IMEI (ni máscara), serie, costo, proveedor, notas privadas o PII.
## 3. Identidad comercial y temporal
product_id = identidad estable Product; variant_id = ID estable de la misma fila Product si pertenece a ProductModel, null para artículo simple; model_id = agrupador opcional. IDs opacos por tenant, no reutilizados; SKU comercial primario activo autorizado inequívoco o null, no usar slug como ID ni generar SKU en consulta.
Toda Price y Availability lleva product_id,variant_id,offer_id,branch_id,offer_kind,data_version,observed_at. offer_kind=shelf: offer_id null, precio configurado y stock de estante por variante/sucursal; used_unit: offer_id opaco ligado a StockUnit.public_id, variante específica; on_order: offer_id opaco de oferta comercial sin revelar proveedor. Precio y disponibilidad anidados deben coincidir exactamente en la tupla con fila padre y su producto y observed_at; data_version monotónica por proyección (la versión compuesta cambia si cualquier dependencia cambia). Backend verificará igualdad entre campos, no expresable de forma general en JSON Schema estándar.
Precio Decimal como string de 2 decimales, moneda ISO 4217 de configuración (PEN solo ejemplo), valid_from/until UTC nullable si fuente no declara; sin inferir vigencia. No mínimos por modelo como precio puntual. Nuevos Product.price; usados StockUnit.sale_price positivo (nunca fallback a Product.price). Oferta bajo pedido solo si regla vigente confirmada del maestro; no costo/proveedor. Promoción condicional no es descuento aplicado: beneficio solo autorizado y contexto verificado; no inventar impuestos o vigencia.
Garantía: nuevos/otros solo policy/unknown, days null, URL autorizada si existe; no plazo inventado. Usados: days de unidad o default de empresa o política; cero explícito, null sin días; batería 0–100 nullable, estado estético registrado nullable. Fotos usadas de unidad exacta, confirmadas y autorizadas, no genéricas. URL comercial canónica del tenant, validar ruta específica de modelo/oferta; si no verificable null.
## 4. Disponibilidad pura (regla permanente)
| status | quantity física vendible | Condición |
|---|---|---|
| available | entero >=1 | confirmada por maestro |
| out_of_stock | 0 | agotado confirmado |
| unknown | null | no verificable, desactualizado o inconsistente |
| on_order | 0 | oferta bajo pedido confirmada, no inventario físico |
Used_unit solo si AVAILABLE, publicada, inspección aprobada, precio positivo y foto pública real, quantity=1; si deja de ser visible, retirar oferta/tombstone (no exponer equipo vendido). On_order solo fila de oferta válida; si deja de serlo, retirar y reflejar estado agregado real. No sumar proveedor al stock ni prometer plazo. Reserva vencida aún no liberada sigue no disponible hasta worker maestro. No ejecutar release_expired, get_or_create, reservas/liberaciones/ajustes, escrituras comerciales indirectas o fallback público/admin. Si discrepancia BranchStock/StockUnit, unknown; no corregir en GET. No prometer reserva.
## 5. Sync consistente
Propuesta: snapshot consistente materializado o MVCC equivalente con corte único de commit para dominios autorizados, ligado a credencial/tenant/branches/scopes. Primera GET sync/changes sin cursor retorna results=[], watermark W opaco, next_cursor de reanudación tras W, has_more=false y snapshot_at. Bootstrap: usar snapshot=W en cada lista autorizada, paginar con cursor estable; todas las páginas mantienen mismo corte, filtros/fields/orden y alcance. Si una lista inicia sin snapshot, abre corte propio. No snapshot mezclado con cursor incompatible.
Journal/outbox transaccional ordenado por commit (no usar updated_at ni sequence precommit sin resolver commits tardíos). W es watermark contiguo, sin saltar commits que aparecen tarde. Feed desde cursor procesa cambios >W, dominio opcional autorizado fijado al cursor; cursor y límite superior fijo del lote/sesión permiten reanudar aunque resultados filtrados estén vacíos; next_cursor siempre no null, has_more false al alcanzar límite. event_id UUID dedupe, operation upsert/delete, entity_id estable, domain, data_version monotónica, occurred_at UTC y branch_id opaco nullable según dominio/scope. No precios, cantidades, PII, servicios/pedidos/reparaciones bloqueados. Una oferta específica que revele estado/precio exige scopes compuestos; si falta uno solo invalidación agregada sin identidad de oferta.
Tombstone para entidad borrada/archivada o retirada de vista antes autorizada; no revelar datos de otros tenants. Cambio de alcance/scope/credencial, cursor vencido o revocado -> invalidar cursor/ETag, 410 y purgar caché fuera de autorización; rebootstrap y reemplazo atómico. Retención propuesta 30 días de journal, snapshot 15 min, sujeto a acuerdo; desconexión mayor a retención obliga resnapshot. Eventos de vigencias generados por procesos autónomos, no por GET. Webhook es aviso de invalidación; nunca watermark ni estado autoritativo.
## 6. Cliente, errores y seguridad
Pedidos y reparaciones fuera de catálogo, sync y webhooks hasta aprobar mecanismo emitido/validado por Web, ligado a cliente, tenant, audiencia, recurso, expiración y revocación. No aceptar teléfono, correo, número de pedido, declaración CRM ni tracking como prueba de identidad. No bloquear catálogo por ese trabajo. Servicios deshabilitados hasta fuente publicable real; no usar órdenes de reparación como catálogo.
Errores cerrados: 400 invalid_request/invalid_field, 401 unauthenticated, 403 forbidden, 404 not_found, 405 method_not_allowed, 410 cursor_expired, 429 rate_limited + Retry-After, 503 unavailable. request_id y detail genérico; no PII ni existencia ajena. 304 sin cuerpo únicamente tras auth. Health mínimo.

Worker autónomo de expiración independiente, atribuir cambios al worker. Casos reserva vencida con/sin pago pendiente, concurrencia, no get_or_create.
- Schema allowlists, campos obligatorios/nullable, precio de unidad/variante, igualdad tupla y observed_at, unknown vs agotado, bajo pedido no suma, usado sin precio/foto/publicación, ausencia costos/IMEI/serie/PII incluso anidados, URL real y scopes de promociones.
- Snapshot concurrencia con commit tardío y cambio entre páginas, watermark sin huecos, tombstones, cursor/scope/fields, revocación, desconexión >retención, cambios de vigencia y dedupe. No GO de implementación/merge sin aprobación.
